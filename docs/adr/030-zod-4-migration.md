# ADR 030: Migrate the repository to Zod 4

**Status**: Accepted
**Date**: 2026-07-26
**Context**: Feature `021-agent-supervision-console`, task T001

## Context

The agent supervision console drives supervised sessions with `@anthropic-ai/claude-agent-sdk`. Installing it failed:

```
npm error Could not resolve dependency:
npm error peer zod@"^4.0.0" from @anthropic-ai/claude-agent-sdk@0.3.220
npm error   Found: zod@3.23.8
```

The repository pinned `zod@3.23.8` in the root manifest and in four extensions (`notepad`, `remote-control`, `git-integration`, `task-vault`). A fifth extension, `speckit-pilot`, imported Zod without declaring it at all, relying on workspace hoisting — itself a violation of Constitution II.

The peer requirement is not avoidable by downgrading: `@anthropic-ai/claude-agent-sdk@0.2.0` already declared `zod@^4.0.0`.

## Decision

Migrate the whole repository to `zod@4.4.3`, pinned exactly, in all six manifests.

## Rationale

**The migration surface was measured, not estimated.** 32 files import Zod (14 core, 18 extension). Every commonly-breaking Zod 3 API was checked and found to have **zero** occurrences: `invalid_type_error`, `required_error`, `errorMap`, `.deepPartial()`, `.strip()`, `.merge()`, `z.nativeEnum`, and `error.errors`. All nine `z.record()` call sites already used the two-argument form Zod 4 requires.

**There is an escape hatch if something does break.** Zod 4.4.3 still publishes a `./v3` subpath export, so any file that resists migration can `import { z } from 'zod/v3'` and keep the exact Zod 3 API while the package version satisfies the SDK's peer range. Nothing in this repository needed it, but the migration was reversible per-file rather than all-or-nothing.

**The test suite is the right safety net.** 4883 tests at ~94% statement coverage. A dependency major is precisely what that suite exists to de-risk.

**Constitution IV points here regardless.** Zod 3 is now the legacy line; "latest stable, actively maintained" is binding independently of the SDK.

## Alternatives considered

**`npm install --legacy-peer-deps`.** Rejected. The Agent SDK uses Zod to validate its own protocol messages, so running it against a major version its author declares unsupported risks silent misvalidation in exactly the layer that produces session runtime state — the one place in this feature where being wrong is invisible. Speed is not worth that.

**Pin an older SDK release.** Rejected — no 0.2.x or 0.3.x release accepts Zod 3.

**Vendor the SDK's Zod 4 as a nested dependency.** Not possible: Zod is a peer dependency, not a regular one.

## Consequences

**Two real behaviour changes were found by the test suite, not by review.**

1. **`.uuid()` is now RFC-strict.** Zod 4 validates version and variant nibbles; Zod 3 used a loose hex-shape regex. Eleven test fixtures used placeholder ids like `00000000-0000-0000-0000-000000000001`, which are not well-formed UUIDs. Production is unaffected — every id is generated by `crypto.randomUUID()`, which emits RFC 4122 v4 — so the fixtures were corrected to `00000000-0000-4000-8000-...` rather than the schema being loosened. The stricter check is a small correctness gain: the schema now rejects ids the application would never produce.

2. **`z.record()` with an enum key is exhaustive.** This is the consequential one. Zod 4 requires every enum member to be present; Zod 3 treated the record as partial. `speckit-pilot` stores `phases` and `phaseGates` as records keyed by a phase-id enum, and real `.pilot/state.json` files never contain every phase. Left unfixed, `readState()` would have returned `null` for **every existing state file** — silent data loss for any card already in flight. Five call sites were switched to `z.partialRecord()`, which is Zod 4's name for the previous semantics.

**Constitution II debt repaid.** `extensions/speckit-pilot` now declares its own `zod` dependency instead of relying on hoisting.

**Verification.** `npm run build:extensions` succeeds; `npm run lint` reports 0 errors; `npx vitest run --coverage` passes 4883/4883 with statements 94.31%, branches 86.14%, functions 90.38%, lines 95.47% — all above the 80% gate.

**Follow-up.** No file needed the `zod/v3` escape hatch, so no compatibility debt was created. Future Zod majors should expect the same two classes of breakage to be the ones worth checking first: tightened string formats, and collection schemas whose default strictness changed.
