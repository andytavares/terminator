Review Screen Redesign

The review screen is where a reviewer spends the most time. Today, navigation is its loudest element, the code gets the least room, and a three-line file is labelled "High risk". This redesign gives the code the room and turns everything else down.

Context and the problem

The review screen (PrReviewView) holds the file list, one file's diff, the comment threads, an inspector with risk and agent tabs, and a footer that moves between files. The previous pass (PR #217) cut the chrome from eleven bands to three. What remains has the same fault the overview had, inside the diff itself:

  • The selected file row is a solid accent block, the brightest thing on screen.
  • Line-number gutters take about a quarter of the pane.
  • Comment prose is set in monospace, larger than the code.
  • A changed line is tinted whole, so the change inside it is not shown.
  • Opening the inspector squeezes the code until it wraps.
  • Risk is scored relative to the other files in the same PR, so in a two-file PR the larger file always reads "High risk 80/100", even at three lines.

Goals and non-goals

  • The code gets the room. At a 1,240px window, code starts 88px from the pane's left edge (today: 198px) and never wraps because a side panel opened.
  • The change inside a line is visible. Changed words in a replaced line get a stronger tint than the line.
  • People's words read as prose. Comments use the UI face at reading size, on a card set apart from the code.
  • A risk label means the same thing in every PR. "High risk" comes from fixed thresholds the repository already uses, not from ranking files against each other.
  • Submit is always one click away, with the pending-comment count on it, as on GitHub and Graphite.
  • One control per job. A file is marked viewed in one place, and one region holds navigation.

Non-goals: the review agent's behaviour, the chapter and reading-order algorithm (ADR 072), split view's layout beyond the shared gutter rules, and the overview (ADR 112).

Why a 3-line file is "High risk"

normalise (github/pr-review-service.ts:148) scales each metric min-max across the PR's own files: (value − min) / (max − min). In a two-file PR, the file with more churn, more importers and more lines gets 1.0 on each, so compositeScore (:183) gives 1.0 × 80 = 80, and riskLevelOf (:230) calls 67 or more "high". The driver label is always phrased "High churn — n commits/90d" (:198), whatever n is. The repository already has absolute thresholds elsewhere: 150 and 400 lines for the queue (:270-272), and churn 20 and 50 and importers 10 and 20 for the signal dots (review/pr-signals.ts:124-125). The per-file level ignores them.

What the best review tools do

Read on 2026-10-14. All four products agree on the shape: a file tree that marks state, a diff that owns the screen, comments as cards, and review submission at the top with its pending count.

Options considered

Option What it is For Against
A. Repair in place Fix the copy bugs, the comment font and the clipped footer. Keep the layout. Small and safe. The code keeps a quarter of the pane, the inspector still squeezes it, and risk still lies.
B. Code-first reader A quiet file tree grouped by chapter, a compact gutter, word-level diff, comment cards, an inspector that overlays instead of taking width, Submit in the header, and absolute risk. Matches the four products studied. Every change reuses existing data and components. Touches the diff rows, so the e2e selectors on gutters and rows change. Word diff needs a library or an algorithm.
C. All files on one long page GitHub's scroll-through-everything model. Familiar. Throws away the chapter order and the "one file, then the next" flow the session model saves (ADR 072).

Decision

Option B. It is the only option that gives the code its room back and makes the risk label honest. The data already exists: chapters, riskScore.metrics, whyHere, the comment threads and the drafts. The one new capability is word-level diff.

The design

Renderings use PR #11 from the overview study, with an illustrative hardware.py diff. The mocks follow your theme and use the app's token values.

1Header. A back arrow to the overview, the PR title, checks, and progress drawn per chapter (one segment each, filled by files viewed) with minutes left. Submit review is always there and counts pending comments. Pause moves into ⋯.
2File tree by chapter. Chapter headers with "2 of 3". Rows are 30px: a state glyph (viewed, unviewed, or a red ring for a high-risk file not yet viewed), the name with its folder muted, comment count and size. The current row is a neutral fill, not the accent. The "why here" text moves to the file header.
3File header. The full path (folder muted, name bold), size, and a risk chip only when the risk is real. Then one muted line: why the file is here, how many files use it, and how often it changes. These replace "Uses 1 · 1 unread". Viewed sits here only, with its key.
4Hunks. A separator row in the UI face names the enclosing symbol ("in class InputPin"). One expand control per gap ("8 unchanged lines"), plus "Show all n lines". No @@ ranges.
5Diff and threads. Gutters are 36px each with no padding columns, and the comment button sits over the line number on hover. Changed words get a stronger tint. Threads are cards in the UI face at 13px, indented to the code, capped at 72ch, with "Pending" on your drafts and a reply field.
6Footer. Key hints on the left. On the right, the previous file by name, and the primary button names the next file: "Viewed, next: api.py ↵". On the last file it becomes "Viewed, submit review".
1The drawer overlays the diff, 380px, with a shadow, so the code keeps its width and does not wrap. Escape closes it. The tabs are "Why this file" (was File) and "Agent".
2Factors in words. One list replaces the bars, the 80/100 and the HEALTH list. Each row says what was measured, the value, and the threshold it crossed. Importers are links. No uppercase labels, and no "?".
3Submit from anywhere. It lists pending comments (each opens its line), takes the summary, and offers three verdicts as cards that say what each does. The primary button names the verdict. It warns, without blocking, when files are still unviewed.

Rules

  • Type: code is --tm-font-mono at 12.5px on a 20px line. Everything people wrote, and all chrome, is --tm-font-ui. There are no hard-coded font families.
  • Color is state: accent only on the primary button and the active tab. Selection is --tm-overlay-strong. Red appears only for a real high risk and for deletions.
  • Word tint: two new tokens, --tm-diff-added-word-bg and --tm-diff-removed-word-bg, about twice the line tint's alpha. Both are added to tokens.css for each theme and checked for AA under the line tint.
  • Plural forms through plural() everywhere ("1 line", "1 importer", "1 commit").

Testing and verification

  • Risk: tests/unit/pr-review-service.spec.ts. A two-file PR of 3 and 1 lines reads low on both. A file with 31 commits in 90 days reads high whatever its neighbours are. No label says "High churn" under the floor.
  • Word diff: tests/unit/word-diff.spec.ts. bounce_time=0.05 to pull_up=True marks only those tokens. An unrelated pair marks whole lines. A 2,000-line hunk finishes inside a set time budget.
  • Rendered: the e2e step from PR #266's harness. Screenshot the review screen at 1,240px and 900px in both themes, with the inspector open and closed. Assert code starts 88px from the pane edge (getBoundingClientRect on the first .c cell) and that no diff line wraps with the drawer open.
  • e2e: tests/e2e/pr-review-diff.spec.ts uses .full-file-row[title=…], Show 20 lines below and Submit review…. Each moves to a role-based selector in the same commit that changes it.

Risks and mitigations

Risk Mitigation
Absolute floors miscalibrated Start from the thresholds the queue and signal dots already ship. Log level counts per PR in the perf script (scripts/perf/git-integration.mts) and tune from real PRs.
Word diff cost on large hunks Only for paired removed and added runs. Skip a run over 500 lines or 10,000 tokens. Compute after first paint, as Zed does.
Overlay drawer hides code It covers the right 380px only while open. Escape closes it, and the line under the drawer that you clicked scrolls into view.
The rail hides file names Every glyph has a tooltip with name and state. f opens the full tree.
Linux visual baselines The gutter and font change moves every diff baseline. Regenerate them in Docker, per the control-heights precedent.

Open questions

  • Word-diff source: add the diff package (jsdiff) to extensions/git-integration/package.json, or write a token LCS? A library is less code. A hand-rolled LCS adds no dependency.
  • Floors for blast radius: the signal dots use 10 and 20 importers. Is "over 5" medium right for a single file, or should it reuse 10?
  • Unviewed files at submit: warn only, as drawn, or require a confirmation as GitLab's "approve with unviewed" does? [GitLab behaviour not verified]
  • Agent tab content: it keeps the Review, Explain and Ask modes. Should the model picker move into ⋯ or settings, since a reviewer rarely changes it mid-review?

Alternatives rejected

  • Repair in place: the code keeps losing a quarter of the pane, and the risk label stays wrong.
  • All files on one page: discards the chapter order and the saved position.
  • Inspector as a fourth column on wide screens only: it still squeezes the code on the laptops most reviews happen on.
  • Hide risk entirely: reviewers lose the one signal that tells them where to slow down. Fixing it is cheaper than dropping it.
