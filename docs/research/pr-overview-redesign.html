PR Overview Redesign

The PR overview shows a reviewer everything at the same volume, so nothing stands out. This redesign orders the screen by the decisions a reviewer makes: can this merge, what is it, where do I start. It keeps every fact the overview shows today.

Context and the problem

Opening a PR from the Reviews tab lands on PrOverviewPanel. That screen has three jobs. It shows whether the PR can merge, explains what it changes, and sends the reviewer into the diff. The layout from 73d390a3 does none of these well, because every element has the same visual weight. Six uppercase labels on the left all look alike, so "No conflicts" looks as urgent as "3 checks pending". The agent's summary and the author's description repeat each other in two boxed panels. Prose runs about 200 characters per line, against a recommended maximum of 75. The numbers a reviewer decides on (size, risk, reading time, chapters) are in the data but sit behind a third tab or nowhere.

Goals and non-goals

  • Status before story. Within the first 120px, the reviewer can see whether the PR can merge and what blocks it.
  • One voice per fact. Each fact appears once. The agent's brief and the author's description are clearly different things and never repeat each other at full weight.
  • Readable prose. Running text stays within 68–72 characters per line at any pane width.
  • A way in. The overview shows the review plan, which already exists as pr.chapters. Any chapter can be the starting point.
  • Problems are loud and settled states are quiet, in both themes, using only tokens from tokens.css.

Non-goals: new data from GitHub, changes to the review screen (PrReviewView), merging from the overview, or requesting reviewers. There is no API for requesting reviewers yet (see open questions).

What the best review tools do

Four products and two usability sources, each read on 2026-10-14. The patterns they agree on drive this design.

Source What it does What we take
GitHub The merge experience, generally available since March 2025, groups status checks by status with failures listed first. Its docs say merge status in the PR header "highlights blockers, missing approvals, and other requirements". Failures first. Mergeability goes in the header.
GitLab Merge request redesign, in progress: merge checks move to the top of Overview, replacing the "description-first layout", so status is visible without scrolling. The stated reason is that users "scroll and hunt through variable-length content". Status before story.
Graphite An info panel at the top right holds status, review status, checks (expandable), reviewers, labels and related tasks. The main column holds stack, description, discussion and files. Properties on the right and reading on the left. Checks collapse to one line.
Linear Diffs Launched May 2026 (changelog). Guided reviews "present the core of the change first". Line counts exclude tests and docs by default. Show the review plan on the overview and let the reviewer start at any chapter.
Cursor Origin A forge built by the Graphite team, in beta since August 2026. A PR has four tabs: Activity, Commits, Checks, Files changed. Conflicts are flagged before merge. [third-party guide; no first-party layout docs found] Conflicts surface before the reviewer acts.
NN/g Progressive disclosure: show the most important options first and the rest on request. Designs with more than two levels "usually have low usability". Two levels at most: a strip cell, then its popover. A signal, then its sentence.
Baymard "The optimal line length for body text is 50–75 characters." WCAG 1.4.8 recommends 80 at most. Cap prose at 68ch.

Options considered

Option What it is For Against
A. Polish in place Keep the left rail and the tabs. Cap the measure, drop the description panel's box, and color the rail values. Smallest diff. No test churn. Size, risk and plan stay hidden. The summary still repeats the description. The left rail stays where nothing else in the app puts properties.
B. Status strip, reading column, properties rail Header with title, people, size and the primary action. A three-cell readiness strip. A Brief, Review plan and Description in a 68ch column. Signals and details in a right rail. Matches GitHub, GitLab, Graphite and Linear. Every fact appears once, at a weight that matches its state. Uses only data the overview already loads. Moves the Insights tab's content and replaces CtaBar, so more specs change.
C. Tile dashboard Big-number cards for checks, size, risk and minutes across the top. Looks rich in a screenshot. Tiles give every number the same weight, which is the problem we have now. They push the brief below the fold.
D. Drop the overview Open straight into the review screen and put the brief in a Guide tab beside the diff, as Linear does. One screen fewer. Removes the go/no-go moment before a review starts. Larger change to PrReviewView and the session flow.

Decision

Option B. Every tool we studied puts mergeability at the top and reading space in the middle. B is the only option that does both and also brings the review plan forward. It needs no new data: every value in the renderings below comes from a field of PrReviewDetail (pr-review.schema.ts:199).

The design

PR #11 with the real title, branches and description text. The file counts, chapters, signals and checks are illustrative, because the screenshot does not show them. Each rendering follows your theme and uses the app's own token values for that theme.

1Header. 19px title with state pill. A meta line with author, branches, opened date, size and estimated minutes. Start review is the one filled button, at the top right, with Mark as ready beside it. This replaces OverviewTopBar and CtaBar.
2Readiness strip. Checks, Reviews and Merge in one row. Settled states are muted, waiting states amber, and blocking states red with a tinted cell. A cell's action sits inside it (see Rendering 2). Replaces ChecksRow, ReviewersRow and MergeStateBadge.
3Brief. The agent's words, in the agent's color (--tm-agent, which tokens.css reserves for work "an agent produced for the reader"). At most four points, and it says what it summarized and when.
4Review plan. pr.chapters as rows: name, top files, highest file risk, file count, added and removed lines, minutes. Hover reveals "Start here", which opens the review at that chapter.
5Description. The author's text at 68ch, with no frame. Inline code without borders and tables with hairline rows only. Clamped to 300px with "Show full description" once a brief exists. Without a brief, it shows in full.
6Rail. Signals carry the Insights tab's content as one line plus one detail each, and hover shows the source. Details hold the facts that were in the left rail. The Insights tab is removed.

Type, color and spacing rules

  • Four text sizes only: 19 (title), 13.5 (reading), 12.5 (meta and rail), 11 (rail headings, uppercase, 0.06em tracking). Today's overview uses seven.
  • Color is state, never decoration. --tm-danger, --tm-warning and --tm-success appear only on icons and the one tinted cell for a blocker. The accent is reserved for the primary button and the active tab. --tm-agent marks agent text.
  • One frame per role. Only the Brief (agent content) and the Review plan (a list of things you can open) get a border. The description, rail and strip are separated by hairlines and space.
  • Icons are lucide, flat, in currentColor, sized in CSS (Principle XII). The ▲ ▼ characters in StatusChecksBar.tsx:135 become ChevronDown.
  • Spacing uses the --tm-space-* scale: 24px pane gutter, 30px between sections, 12px inside them. Controls are --tm-control-height or -sm.

Risks and mitigations

Risk Mitigation
Rail squeezes the column The rail is fixed at 300px, and the column needs 68ch (about 560px). Under 900px of pane the rail drops below. Under 640px, Rendering 4 applies.
Signals while insights load pr.insights is null until analysis finishes. The rail shows "Analysing…" in the Signals slot, as InsightsPanel does today. Risk comes from chapters and shows at once.
Markdown overrides leak Every override is scoped under .pr-overview-reading. Verify the Markdown in the review inspector and in comments by rendering them before and after.
Patch coverage gate components/** is excluded from coverage, so measure with --coverage.include on the new files and report it in the PR.
Chapter start lands on a stale session setCurrentChapter runs before the view switches. The spec covers a resumed session where currentChapterId was already set.

Open questions

  • Request a reviewer from the strip? githubAPI has no request-reviewers call (api/github.ts). The Reviews cell stays read-only unless we add one.
  • Check durations in the popover need StatusCheckSchema to carry start and end times, which it does not today (pr-review.schema.ts:83). Ship without them, or extend the fetch?
  • Cancel a running summary? ADR 111 puts the child process in liveRuns, but no channel cancels a single summary. Add review-agent:cancel-summary, or show no Cancel button.
  • Structured brief? Should SummaryOutputSchema return { points: string[], notDone?: string } instead of Markdown, so the "Not done" line can always be styled? This changes ADR 111.
  • Line counts like Linear's? Linear excludes tests and docs from line counts by default. The header could show implementation lines and give the total on hover. understandability.linesToRead already leaves out lock files.

Alternatives rejected

  • Polish in place: fixes the look, but size, risk and the plan stay hidden.
  • Tile dashboard: equal-weight numbers are the problem we are fixing.
  • Drop the overview: loses the go/no-go moment and changes the review screen.
  • Keep the Insights tab: a third tab is where the decision numbers went to hide.
  • Left rail: no tool we studied puts properties on the left, and a left rail pushes the reading column off the reviewer's focal line.

Amended: four sections (2026-10-30)

The overview is now four fixed sections (ADR 112, Amended). The header and the status strip stay pinned. The tabs are Change and Discussion · N, and each scrolls on its own. The properties rail sits beside both tabs with its own scroll; below 900px it is a third tab, Properties. The description is always clamped, a comment is clamped at 160px, and only the last three comments show. Icons are flat.
