Code Review Revamp

Status DraftDate 2026-09-27Surface Code Reviews tab + new Reviews global tab

Five changes you asked for (R1–R5) and five drawn from current diff and review tools (S1–S5). Every change has a rendering below; the interactive ones respond to clicks.

Context

Code review takes a large share of your day. The Code Reviews tab already splits a PR into chapters, scores risk, and keeps your place. Four things still slow you down. It sees one repository at a time. It shows callers before the code they call. Its coverage and complexity numbers don't measure the PR's own code. It has no agent. And every push from the author wipes your viewed-file progress, which is the worst of these when you are interrupted mid-review.

Goals and non-goals

  • G1 One dashboard of every open PR that needs you, across repositories, including requests made to your teams.
  • G2 Comments show or hide with one key, without losing track that they exist.
  • G3 A function's hunk is shown before any hunk that calls it.
  • G4 Complexity, risk, coverage, health and understandability, each stating where its number came from, or "not measured".
  • G5 An agent reviews a PR, chapter, file, hunk or line range on request. Results stay private. Nothing reaches GitHub until you click Post.
  • G6 A push, a restart or a two-hour meeting never costs you your place.

Non-goals: approving automatically; the agent editing the branch or writing to the PR; GitLab or Bitbucket; merge queues; replacing GitHub for PRs you author.

Decisions

D1 · How to find definitions and their uses

A. Extend the existing import regex

IMPORT_RE already links files by relative imports. Cheap, but JS/TS only and file-level. It can't see a call inside the same file and can't order hunks.

B. Tree-sitter in WASM

web-tree-sitter 0.27.0 (published 2026-08-30) with the prebuilt grammars in @vscode/tree-sitter-wasm 0.3.1: TypeScript, TSX, JavaScript, Python, Go, Rust, Java, C#, Ruby, PHP, C++, Bash, CSS. Parses base and head of each changed file and gives definitions and references per hunk. No native build. ADR-010 already names Tree-sitter as its v2.

C. Language servers

Precise, but it needs a server per language and a checkout with dependencies installed. Too slow to start for a review.

Files in a language without a grammar fall back to A, then to today's tiers.

D2 · Where the review agent runs

A. Headless claude -p with a JSON schema, read-only tools

claude -p --output-format json --json-schema … --tools "Read,Grep,Glob" --session-id <uuid> in a detached worktree at the PR head. Structured output, quiet, and it can't post: without Bash it can't run gh. ADR-026 keeps headless spawn for self-review, and this extension already uses child_process (git/git-service.ts, ipc/merge-flow.ipc.ts). Flags checked with claude --help and the headless docs.

B. Interactive agent in a terminal tab

Foundry's pattern (ADR-026): visible and steerable. But the result has to be handed back through a file, and a new tab for every "what does this line do?" is noise.

C. Reuse Foundry's supervised runner

Not allowed. Constitution Principle II forbids one extension importing another's code.

A, plus Continue in terminal, which opens claude --resume <session-id> in a terminal tab through api.pty.openTerminalTab when you want a conversation.

D3 · Where the dashboard gets its PRs

A. Run today's per-repo query for every workspace project

One query per repo, and it misses repos you haven't opened in Terminator.

B. GitHub search, one query per section

Cross-repo, filtered on the server. The documented qualifiers cover this: user-review-requested:@me, team-review-requested:, reviewed-by:, involves:, review:changes_requested, draft:, archived:. gh search prs --review-requested=@me exists in gh 2.97.0.

D4 · What a review session is keyed by

A. Keep headSHA in the key and copy on push

Smallest change, but "viewed" still means "viewed at some SHA we threw away".

B. Key by repo and PR; store the SHA each file was viewed at

Lets S1 diff from your SHA to the new head. Matches GitHub's own model: FileViewedState.DISMISSED is documented as "The file has new changes since last viewed" (checked by GraphQL introspection).

R1Review dashboard

A new global tab, Reviews, registered with api.sidebar.registerGlobalTab. Each section is a saved GitHub search, as in gh-dash, so it covers every repository you can see. The count of PRs waiting on you shows on the tab itself. The per-repo Code Reviews tab stays; opening a row takes you to it.

Sections and their queries (editable in settings; defaults shown):

  • Re-review: is:pr is:open archived:false reviewed-by:@me -author:@me, kept only if a commit landed after your latest review.
  • Requested of you: is:pr is:open archived:false user-review-requested:@me
  • Requested of your team: is:pr is:open archived:false team-review-requested-user:@me, minus rows already above.
  • My PRs: is:pr is:open author:@me, labelled by what's blocking: changes asked, CI failing, approved.
  • Involved: is:pr is:open involves:@me -author:@me

Opening a row needs a local checkout. The dashboard matches the row's owner/repo against the origin remote of each workspace project. With no match it offers Clone and review.

R2Comment visibility

One control in the diff toolbar with three states, cycled by c. All shows every thread; resolved ones are dimmed. Unresolved hides resolved and outdated threads. Hidden removes threads from the flow entirely and leaves a count in the gutter, so you still know a conversation is there. Agent notes (R5) have their own switch, shift+c. Your choice is remembered.

Needs: threads fetched from GraphQL reviewThreads so isResolved is known (the field exists on PullRequestReviewThread, checked by introspection). ThreadSchema gains resolved: boolean.

R3Definitions first

The order changes from files to hunks. Tree-sitter reads each changed hunk and records what it defines and what it references. A hunk that calls computeRiskScore depends on the hunk that changes computeRiskScore. A topological sort of that graph gives the reading order; files that reference each other (a cycle) are kept together as one step. Chapters stay: they group the ordered hunks, so a chapter never opens with a call into a later one.

Rules, in order:

  1. A hunk that defines or changes a symbol comes before any hunk that references it.
  2. A test comes right after the last hunk it exercises, not at the end of the PR.
  3. Among hunks that are free to go next, the one in the same file as the last one wins; then higher risk; then larger.
  4. Lock files and generated files (today's tier 3) stay last and collapsed.
  5. Your manual drag-reorder (fileOrderOverrides) still wins.

Each step shows a one-line reason, replacing today's fixed whyHere strings.

R4Insights

A Review brief at the top of the Overview, plus a line per file and a gutter mark per function. Every figure names its source. When nothing measured it, it says "not measured" rather than showing a guess.

Measure How it's computed When it can't be measured
Complexity Per-function cyclomatic count on base and head ASTs; the change is head minus base. Replaces the keyword count, as ADR-010's v2 path describes. No grammar: today's keyword count, labelled "approximate".
Risk Today's computeRiskScore, but churn and blast radius run at the PR head in the review worktree, and coverage uses the row below. Fewer than 2 signals: "not measured" (today's rule).
Test coverage 1. The patch-coverage status check, when CI publishes one (COVERAGE_CHECK_NAMES already lists codecov, coveralls, sonar and others). 2. coverage/ inside the review worktree, only if its HEAD is the PR head. "Not measured", plus how many changed source files have a changed test beside them.
Code health Counts, in added code only: functions over 80 lines, nesting deeper than 4, more than 5 parameters, new any, @ts-ignore, eslint-disable, TODO; duplicate blocks from the existing detectDryViolations. No grammar: the text-based flags only.
Understandability From the R3 graph: lines left to read after the Semantic filter and tier 3, new exported symbols, longest definition chain, cross-chapter references. Easy / Moderate / Hard, with the thresholds in settings. Always measurable.

R5Agent review

Select lines, a hunk, a file, a chapter or the whole PR, then press a or click Ask agent. Pick Review, Explain or type a question. Results arrive in a side panel and as dashed notes in the diff that only you see. Each finding has Post as comment, which opens the comment composer filled in for you to edit; nothing reaches GitHub until you send it.

How a request runs

Scopes: line range, hunk, file, chapter, PR. For the PR scope the output adds a walkthrough: one paragraph per chapter saying what changed and then what it affects (after Linear Diffs), shown at the top of the Overview and cached per head SHA.

Finding shape: { severity: 'must-fix' | 'suggestion' | 'nit' | 'question', path, startLine, endLine, side, title, body, suggestedCode? }. The severity values are rendered into the prompt from the schema constant, so the agent is always shown the closed set.

Controls: model and effort in settings (review.agentModel, default opus), a per-request timeout (default 5 min), one run per scope at a time, Cancel kills the process.

S1Since your review

When the author pushes, your progress stays. Each file remembers the SHA you viewed it at. Files unchanged since then stay ticked; changed files show Changed since you viewed and open on the diff from your SHA to the new head. Viewed state is also written to GitHub (markFileAsViewed, input pullRequestId, path), so the web UI and your other machines agree.

S2Resume card and private notes

Reopen a PR after more than 15 minutes away and a card says where you were and what moved. Press m on any line to leave yourself a note. A note containing ?? is a question, and the card offers to send it to the agent (from revdiff). Notes never leave your machine.

S3Keyboard-first review

Single keys inside the review surface, handled on renderer keydown (never globalShortcut, which takes an OS-wide claim). Escape is left alone because a double Escape leaves the extension. ? shows this sheet.

S4Moved code collapses

A block deleted in one place and added unchanged elsewhere (3 or more lines, compared with whitespace normalised) collapses to one row that links both ends. A moved block with small edits shows only the edits. This uses the same tree-sitter parse as R3. Today's Semantic filter (classifyHunk) already hides formatting-only hunks and stays.

S5One review, not N comments

Comments you write go into a pending review instead of posting one by one. GitHub supports this directly: "To create a pending review for a pull request, leave the event parameter blank" (REST docs). You can edit or delete drafts until you submit. The author gets one notification.

Testing and verification

Each PR is done when these exit 0 from the worktree, per the constitution and this repo's checklist: 

npm run format
npm run lint
npx vitest run --coverage          # all pass, patch coverage ≥ 80%
npx playwright test tests/e2e/git-integration-smoke.spec.ts

Tests written first, per unit:

  • reading-order.spec.ts: the seven-file example above yields the proposed order; a cycle (A calls B, B calls A) stays together; a file with no grammar falls back to tiers; manual overrides win.
  • symbols.spec.ts: definitions and references for TS, TSX, Python and Go fixtures shaped like real hunks (not empty files).
  • insights.spec.ts: coverage source order (check, then worktree at head, else "not measured"); a && inside a string is not a branch.
  • review-agent.spec.ts: the spawned argv contains --tools Read,Grep,Glob and no Bash; output failing the schema becomes an error, never a partial list; timeout and cancel kill the process.
  • pr-review.store.spec.ts: a new head keeps viewed files whose content is unchanged; a v1 session migrates.
  • E2E: open a PR, toggle comments, confirm the rendered DOM (not a store call) hides threads; reload and confirm the choice held.

Then a live run on a real PR (#213, 109 files): screenshot every surface in the running app, and time one agent review at each scope.

Risks and mitigations

Risk Mitigation
Parsing 100+ files blocks the main process Parse in a worker thread; parse only changed files; cache by blob SHA.
Grammar WASM adds weight to the extension Load a grammar on first use of its language. [UNVERIFIED] total size not measured yet.
Agent cost and wait on large PRs Default scope is the selection; PR scope shows the file count first; one run per scope; results cached per head SHA.
Agent findings are wrong Private by default, never auto-posted, each can be dismissed; dismissals are kept so the same finding isn't shown twice.
Search API rate limits on the dashboard One GraphQL request for all sections using aliases; refresh on focus and at most every 2 min; show the reset time as today's RATE_LIMITED path does.
Worktrees pile up on disk Keep the 5 most recent; remove on PR close; git worktree prune at start.
Force-push removed your old SHA Old heads are fetched into refs/terminator/review/* while you review; if absent, show the whole file with a note.

Alternatives rejected

  • Posting agent findings as GitHub review comments by default: you asked for the opposite.
  • LSP for reading order: needs per-language servers and installed dependencies.
  • An interactive terminal agent per question: a tab per question is noise; kept only as "Continue in terminal".
  • Reusing Foundry's runner or risk grader: Principle II forbids cross-extension imports.
  • Octokit for the dashboard: ADR-009 keeps all GitHub calls on gh.
  • A single composite "health score": hides which signal moved; five labelled measures instead.
